# Release v1.0.0 — Railway Deployment Runbook

## 1. Prerequisites

Before starting, ensure the following are in place.

### Accounts and access

- [ ] A [Railway](https://railway.app) account (Hobby plan or above — the free tier does not allow persistent deployments).
- [ ] Access to the GitHub repository that hosts this project.
- [ ] Railway granted OAuth access to the GitHub organization/account that owns the repository.

### Tools (local machine)

- [ ] [Railway CLI](https://docs.railway.app/develop/cli) installed and authenticated:

  ```bash
  npm install -g @railway/cli
  railway login
  ```

- [ ] Docker installed (for local image verification before deploying):

  ```bash
  docker --version   # Docker 24+ recommended
  ```

### Backend

- [ ] The backend API is deployed and reachable at a stable URL (e.g., `https://library-api.railway.internal/api` or an external URL).
- [ ] You have the full `VITE_API_BASE_URL` value ready.

> If the backend is not yet available, set `VITE_USE_MOCK_API=true` for this release and update it once the backend is live.

## 2. Repository Preparation

Confirm the following files exist and are committed to the branch being deployed (typically `main`):

| File | Purpose |
|---|---|
| `Dockerfile` | Multi-stage build: Node builder + Nginx server |
| `nginx.conf` | Nginx server block template with SPA routing |
| `.dockerignore` | Keeps the build context clean |

Verify the build passes locally before deploying:

```bash
# Build the image locally using the same variables you will set in Railway
docker build \
  --build-arg VITE_API_BASE_URL=https://your-backend.railway.app/api \
  --build-arg VITE_USE_MOCK_API=false \
  --build-arg VITE_ENVIRONMENT=production \
  -t library-portal:v1.0.0 .

# Run and confirm the app loads
docker run --rm -e PORT=8080 -p 8080:8080 library-portal:v1.0.0
# Open http://localhost:8080 in a browser — the login page must appear
```

If the local build fails, resolve it before proceeding. Do not deploy a broken image.

## 3. Create the Railway Project

1. Go to [railway.app/new](https://railway.app/new).
2. Select **Deploy from GitHub repo**.
3. Authorize Railway to access the repository if prompted.
4. Search for and select the `library-portal` repository.
5. Railway will create a new project. Rename it if desired (e.g., `library-portal`).

> Railway may immediately attempt to auto-detect and deploy the project. Let it fail or cancel it — you will configure environment variables in the next steps before the first real deployment.

---

## 4. Create the Web Service

If Railway did not automatically create a service after step 3:

1. Inside the project, click **+ New Service**.
2. Select **GitHub Repo** and choose the `library-portal` repository.
3. Select the branch to deploy (typically `main`).

Railway will detect the `Dockerfile` automatically and switch the builder to **Dockerfile** mode.

## 5. Configure Environment Variables

> **Critical:** `VITE_*` variables are baked into the bundle at build time by Vite. They must be set **before** the first deployment is triggered. Changing them after deployment requires a full rebuild.

In the Railway dashboard:

1. Open the **library-portal** service.
2. Go to the **Variables** tab.
3. Add each variable below using **+ New Variable** or bulk-import via the **RAW Editor**.

### Required variables

| Variable | Value | Notes |
|---|---|---|
| `VITE_API_BASE_URL` | `https://your-backend.railway.app/api` | Full URL to the backend API. |
| `VITE_USE_MOCK_API` | `false` | Set to `true` only if deploying without a backend. |
| `VITE_ENVIRONMENT` | `production` | Used for debugging labels; no functional effect. |

### Optional variables

| Variable | Value | Notes |
|---|---|---|
| `VITE_API_HOST` | _(empty)_ | Only needed if `VITE_API_BASE_URL` is not set. |
| `VITE_API_PORT` | _(empty)_ | Only needed if `VITE_API_BASE_URL` is not set. |

### Runtime variable (set automatically by Railway)

| Variable | Set by | Notes |
|---|---|---|
| `PORT` | Railway (automatic) | Nginx reads this at container start via `envsubst`. Do **not** set this manually. |

> Railway automatically passes all service variables as Docker build arguments when building from a Dockerfile. The `ARG` declarations in the `Dockerfile` pick them up without any additional configuration.

## 6. Configure the Build and Start Settings

In the Railway dashboard, open the **Settings** tab of the service.

### Build configuration

| Setting | Value |
|---|---|
| Builder | Dockerfile (auto-detected) |
| Dockerfile path | `./Dockerfile` (default — leave as is) |
| Build context | `.` (default — leave as is) |

### Networking

| Setting | Value |
|---|---|
| Internal port | Leave empty — Railway reads `PORT` from the running container |
| Health check path | `/` |
| Health check timeout | `30s` |

> Railway will send a `GET /` request to the container after deployment. Nginx returns `200` for the root path, so the health check will pass without any additional configuration.

### Restart policy

Set the restart policy to **On Failure** with a maximum of 3 retries.

## 7. Trigger the First Deployment

Once the variables are saved:

1. Go to the **Deployments** tab of the service.
2. Click **Deploy Now** (or push a new commit to `main` — Railway deploys automatically on every push).
3. Watch the **Build Logs** in real time.

### Expected build log sequence

```
Cloning repository...
Building Dockerfile...
[Stage 1 - builder]
  => [1/6] FROM docker.io/library/node:20-alpine
  => [2/6] WORKDIR /app
  => [3/6] COPY package*.json ./
  => [4/6] RUN npm ci
  => [5/6] COPY . .
  => [6/6] RUN npm run build

[Stage 2 - nginx]
  => [1/3] FROM docker.io/library/nginx:1.27-alpine
  => [2/3] COPY nginx.conf /etc/nginx/templates/default.conf.template
  => [3/3] COPY --from=builder /app/dist /usr/share/nginx/html

Successfully built <image-id>
Deployment succeeded
```

If the build fails, see the [Troubleshooting](#12-troubleshooting) section.

## 8. Verify the Deployment

After the build succeeds and the container is running:

1. Check the **Logs** tab for the Nginx startup message:

   ```
   /docker-entrypoint.sh: Configuration complete; ready for start up
   ```

2. Confirm the health check is passing (green indicator next to the deployment in the **Deployments** tab).

3. Open the service URL provided by Railway (visible in the **Settings** tab under **Domains**).

4. Confirm the login page loads and that credentials `reader / reader` work.

## 9. Assign a Public Domain

Railway provides a randomly generated subdomain by default. To use it or configure a custom domain:

### Use the generated subdomain

1. Go to **Settings** → **Networking**.
2. Under **Public Networking**, click **Generate Domain**.
3. Copy the generated URL (e.g., `library-portal-production.up.railway.app`).

### Use a custom domain

1. Go to **Settings** → **Networking** → **Custom Domain**.
2. Enter your domain (e.g., `portal.yourlibrary.org`).
3. Railway will show a `CNAME` record to add in your DNS provider.
4. Add the `CNAME` record at your DNS provider:

   | Type | Host | Value |
   |---|---|---|
   | CNAME | `portal` | `library-portal-production.up.railway.app` |

5. Wait for DNS propagation (typically 5–30 minutes). Railway will automatically provision a TLS certificate via Let's Encrypt once the DNS record is verified.

## 10. Post-Deployment Checks

Run through the following checklist after the domain is live.

### Functional checks

- [ ] Login page loads at the root URL.
- [ ] Login with `reader / reader` succeeds and redirects to `/library`.
- [ ] At least one book card is visible in the library.
- [ ] Clicking a book card opens the detail modal.
- [ ] The **Read online** button opens the PDF reader in a new tab (if a `pdfUrl` is present).
- [ ] The profile icon opens the dropdown with **My account** and **Logout**.
- [ ] Navigating to `/account` shows the account page.
- [ ] The language switcher on the account page changes the UI language.
- [ ] The footer **Change log** link opens `/changelog` with formatted entries.
- [ ] Typing a search term filters the book list.
- [ ] Logging out returns to the login page.

### Deep-link / SPA routing check

Navigate directly to the following URLs in the browser address bar (do not use in-app navigation). Each must load correctly, not return a 404:

- [ ] `https://your-domain.com/library`
- [ ] `https://your-domain.com/account`
- [ ] `https://your-domain.com/changelog`
- [ ] `https://your-domain.com/login`

> These work because `nginx.conf` routes all unmatched paths to `index.html`, letting Vue Router handle client-side routing.

### Performance check

Open the browser DevTools **Network** tab and reload:

- [ ] `index.html` is returned with `Cache-Control: no-store` (confirm in response headers).
- [ ] JS and CSS bundles are returned with `Cache-Control: public, immutable`.
- [ ] Response is gzip-encoded (`Content-Encoding: gzip`).

### Security headers check

Using [securityheaders.com](https://securityheaders.com) or DevTools, confirm the following response headers are present on every page:

- [ ] `X-Content-Type-Options: nosniff`
- [ ] `X-Frame-Options: SAMEORIGIN`
- [ ] `Referrer-Policy: strict-origin-when-cross-origin`

## 11. Rollback Procedure

Railway keeps a history of all deployments. To roll back to the previous version:

### Via the dashboard

1. Open the **Deployments** tab of the service.
2. Find the last successful deployment before the current one.
3. Click the **...** menu on that deployment row.
4. Select **Rollback to this deploy**.
5. Railway will re-activate the previous image without rebuilding.

### Via the Railway CLI

```bash
# List recent deployments
railway deployments

# Roll back to a specific deployment ID
railway rollback <deployment-id>
```

> A rollback re-activates a previously built image immediately. No rebuild occurs, so the rollback takes effect in under a minute.

## 12. Troubleshooting

### Build fails: "Cannot find module" or "vite: command not found"

`devDependencies` (including Vite) must be installed during the build. Confirm that the `Dockerfile` runs `npm ci` **without** `--omit=dev` in the builder stage. Check the current `Dockerfile` at the line:

```dockerfile
RUN npm ci
```

This installs both `dependencies` and `devDependencies`, which is correct for the build stage.

---

### Build fails: VITE_ variable is empty or undefined

Vite emits a warning when a referenced env variable is missing. Verify that all required variables are set in the Railway **Variables** tab before triggering a build. Variables added after the last build require a new deployment to take effect.

---

### Container starts but returns 502 or connection refused

Railway health check is failing. Check the **Logs** tab for Nginx startup errors.

Common causes:

- `PORT` variable conflict: Do not manually set `PORT` in the Railway Variables tab. Railway injects it automatically.
- Template syntax error in `nginx.conf`: Ensure `${PORT}` is the only substitution variable in the template.

---

### SPA routes return 404

The Nginx `try_files` directive is not working. Confirm the deployed `nginx.conf` contains:

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

If it does not, the `nginx.conf` file may not have been committed to the repository before deploying.

---

### API calls fail (network errors or CORS)

- Confirm `VITE_API_BASE_URL` was set correctly at build time.
- Check the browser DevTools **Network** tab for the request URL — it should point to the backend, not `localhost`.
- If it still points to `localhost`, the variable was not injected during the build. Add it to Railway Variables and redeploy.
- Confirm the backend service has CORS configured to allow the frontend domain.

---

### Changes to VITE_ variables have no effect after redeployment

`VITE_*` variables are embedded in the compiled JavaScript. Simply restarting the container does not re-bake them. You must trigger a full rebuild after changing these variables. In the Railway dashboard, click **Redeploy** (not **Restart**).
